# 进项税转出 / 印花税：纳税所属期批次版

本目录是一组用于合并到现有 Tauri + React 项目的源码补丁，不是完整可直接启动的仓库。它将流程主键改为**纳税所属期结果集**；不引入“操作当期”字段。认证期间/凭证期间作为所属期结果集下面可追加的匹配来源范围。

## 新流程规则

- 进项转出、印花税分别按模块管理纳税所属期批次。
- 用户在第一次匹配前选择纳税所属期（单期或跨期）；跨期最多 3 个连续自然月。
- 新建批次的起始月必须严格晚于本模块此前已建立的最近纳税所属期结束月。中间月份可跳过；系统不创建空结果集。例如最近批次为 202601–202603，后续可选 202607–202609，也可选 202609，但不能新建 202604–202606 或 202609 之前的所属期。
- 同一纳税所属期结果集下可添加一个或多个不重叠的来源范围：进项转出按认证期间，印花税按凭证期间。所有已选范围的明细都展示在该所属期的复核工作区中。
- 同一模块同时只允许一个未完成的所属期批次。确认锁定后，才能新建更晚的批次；历史所属期如需补充或修改，由管理员按所属期解锁。
- 已确认转出的明细不可删改。管理员解锁后新增的明细使用补充凭证批次，沿用原纳税所属期；原确认行仍保持锁定。
- 新增规则后，对同一来源范围再次点击匹配，会重算该范围内尚未人工判定的机器结果；人工结论不会被覆盖。未命中且未人工判定的明细仍可再次参加匹配。跨批次机器命中、已确认转出、或人工设为计入的明细不会作为新机器匹配候选；仍会在复核表中显示，并标记为其他所属期已命中/确认。

## 前端用户操作

### 进项税转出

1. 打开“匹配与复核”，先选纳税所属期，再选认证期间，点击“匹配 / 加入本所属期”。首次操作会创建所属期结果集；再次选择同一所属期可追加另一个认证期间范围，已选范围会合并展示。
2. 对全量表格筛选、搜索、查看规则命中与凭证信息；逐行或批量设为转出/不转出、采纳机器结论、恢复机器结论、填写备注，并可修改转出税额。尚未确认前均可复核修改。
3. 在结果集管理页按纳税所属期找到批次，先导出当前待确认清单交会计团队做账。导出后若再修改，需要重新导出。
4. 会计做账后，打开“确认”对话框填写凭证号、入账日期、做账人；纳税所属期只读显示，因为已在创建匹配批次时选定。确认后结果集锁定。
5. 管理员可在结果集列表中解锁任意历史纳税所属期。解锁后沿用该所属期继续修改/追加，新增结果导出为补充清单；会计回填新凭证信息后再确认。
6. “已确认明细查询”支持纳税所属期起止查询，可追加认证期间和关键词筛选，并导出 Excel。

### 印花税

- 复核方式相同，来源期间改为凭证期间。可人工指定印花税子目；类别冲突、待复核或缺少有效子目会阻止确认并给出提示。
- “信息采集表”按纳税所属期选择结果集，按配置的父级税目/子目汇总金额与税金，使用税局 Excel 模板导出。模板路径、工作表、起始行、列映射和固定单元格需要首次配置。
- 查询页按纳税所属期范围查询已确认明细，并显示对应来源凭证期间。

## Schema / 后端调整

- `tax_runs` 仍承载结果集状态，但唯一批次键改为 `(module, filing_period_from, filing_period_to)`，所属期在匹配创建时写入，不再等到确认时决定。
- 新增 `tax_run_sources`，记录同一所属期结果集下的认证/凭证期间来源范围；它是来源明细展示与匹配的权威范围表。
- 旧人工修改表从 `UNIQUE(detail_id)` 迁移为 `UNIQUE(run_id, detail_id)`，会保留原有人工结论行。
- 旧 `src_period_from/src_period_to` 列暂时保留作 v2 兼容/迁移字段；新业务逻辑以 `tax_run_sources` 为准，它们不是操作当期字段，也不再作为批次键。
- 同一来源范围的规则重跑只更新尚未人工判定的当前机器结果。命中事实按发票明细全局阻止未来所属期重复机器匹配；未命中不写命中事实，因此可在未来批次重试。人工结论按 `(run_id, detail_id)` 保存，历史所属期之间互不覆盖。
- 管理员解锁、重锁、日志和凭证批次继续以 `tax_run.id` 操作；该 ID 现在对应一个纳税所属期结果集。

## 合并与迁移

1. 将 `src-tauri/src/tax_workflow/`、`src-tauri/src/commands/tax_workflow.rs` 和 `src/features/tax-workflow/` 合并到相同路径。
2. 将 `src-tauri/src/db/schema_tax_workflow.rs` 加入项目，并在 `src-tauri/src/db/mod.rs` 声明 `pub mod schema_tax_workflow;`。合并 `src-tauri/src/db/schema.rs` 中初始化调用：`super::schema_tax_workflow::init_tax_workflow(conn)?;`。
3. 在 crate 根模块声明 `pub mod tax_workflow;`，commands 模块声明 `pub mod tax_workflow;`，并把该文件中的 Tauri commands 注册到现有 `generate_handler!` / Specta 导出器。
4. 按真实应用适配 `commands/tax_workflow.rs` 的 `DbState`、数据库锁和 `AppRuntimeState.username` 绑定。
5. 把 `InputTaxTransferPage` 与 `StampTaxPage` 接入现有路由和导航；确认 UI 已有 `button`、`dialog`、`input`、`label`、`sonner`，并配置 Tauri dialog 插件。
6. 首次启动新版本前备份 SQLite 文件。初始化会为已有 `tax_runs` 回填 `tax_run_sources`，并重建所属期唯一索引。如果存在 v2 的 `open/reopened` 旧批次但其 `filing_period` 为空，系统不会猜测纳税所属期；应先在备份副本中处理该未完成旧流程，再升级。
7. 在 `app_admins` 中插入管理员用户名（忽略大小写，需与运行时登录用户一致），否则历史所属期解锁/重锁不可用。
8. 印花税模板未包含在本次上下文；用户需在页面选择模板并配置映射后使用。

## 项目接入假设与验证状态

- Rust 代码仍依赖现有项目提供的数据库 State、登录用户名、Tauri command 注册和表结构。
- 本补丁上下文没有完整 React 应用、依赖安装目录和税局模板，因此不能验证完整应用构建与端到端流程。
- 本执行环境没有 `cargo` / `rustc`；Rust 尚未经过实际编译。前端 TSX 已完成语法转译检查；SQLite 批次 DDL 已在内存库验证。部署前请在完整仓库执行 `cargo fmt`、`cargo check`、前端构建和迁移/业务端到端测试。
